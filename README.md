# DB 인덱스 자료구조 - 왜 트리가 기본이고 해시는 언제 쓰나

> 시작: 2026-10-29. 계기: 어크로스비 인터뷰 준비 중 자료구조 이야기에서 나온 질문.
> 성격: 학습 실험. 결론은 직접 잰 결과로만 적는다.

## 1. 출발 질문

DB 인덱스는 보통 트리(B-tree, B+tree)를 쓴다. 목적이 빠른 조회라면 해시맵이 더 빠를 텐데 왜 트리가 기본인가?

- **내 처음 가설**: 데이터를 저장하는 규모(사이즈)에 대한 트레이드오프 때문이다.
- **대화에서 들은 다른 설명** (아직 검증 전):
  1. 기능: 해시는 동등 조회(`=`)만 된다. `BETWEEN`, `<`, `>`, `ORDER BY`, `LIKE 'abc%'`, `MIN/MAX`, 복합 인덱스 앞 컬럼 조회는 해시로 불가능하거나 풀스캔이 된다. B+tree는 리프가 정렬되고 연결돼 있어 시작점을 찾고 훑으면 된다.
  2. 디스크, 캐시: fan-out이 커서 수억 건도 3~4단계로 도달하고, 상위 레벨은 메모리에 있다. 해시는 접근이 랜덤이라 locality가 없다.
  3. 성장 방식: 해시는 차면 리해싱이 필요하고, B-tree는 페이지 단위 split으로 조금씩 커진다. 내 "규모" 가설은 여기에 가깝다(공간 자체보다 성장 방식과 I/O 패턴).
  4. 해시 인덱스도 실제로 쓰인다: PostgreSQL `USING HASH`, MySQL MEMORY 엔진 기본 해시, InnoDB Adaptive Hash Index(B-tree 위 캐시), Redis 같은 KV 저장소.
- 한 줄 정리(검증 대상): "동등 조회만 있으면 해시, 범위나 정렬이 섞이면 트리."

## 2. 검증하며 의심할 지점

대화 설명을 그대로 믿지 않고 확인할 것들이다.

- "해시는 리해싱이 운영상 악몽"이 맞나? PostgreSQL 해시 인덱스는 버킷을 하나씩 나누는 방식으로 커진다고 알려져 있다(선형 해싱 계열). 전체를 한 번에 재배치하지 않을 수 있다. [확인 필요 - PG 소스 `src/backend/access/hash/README`]
- "수억 건도 3~4단계"가 키 크기와 무관하게 맞나? 키가 길면 fan-out이 줄어 높이가 늘 것이다.
- 해시가 동등 조회에서 실제로 얼마나 빠른가? 트리 상위 레벨이 캐시에 있으면 차이가 작을 수 있다.
- 인덱스 크기: 같은 데이터에서 btree와 hash 중 어느 쪽이 큰가? (내 처음 가설의 "사이즈" 부분을 직접 잰다)
- 세 번째 선택지: LSM-tree(RocksDB, Cassandra)는 쓰기가 많은 곳에서 왜 쓰나.

## 3. 실험 목록

### 실험 1. PostgreSQL btree vs hash (우선)

- 데이터: 100만 / 1,000만 / 1억 행(가능한 만큼). 키는 bigint와 긴 문자열(예: 주문번호 30자) 두 가지.
- 잴 것:

| 항목 | 방법 |
|---|---|
| 동등 조회 지연 | `EXPLAIN (ANALYZE, BUFFERS)` + pgbench 커스텀 스크립트, p50/p99 |
| 범위 조회 | `BETWEEN`, `ORDER BY ... LIMIT` - 해시 인덱스가 쓰이는지 실행 계획 확인 |
| 인덱스 크기 | `pg_relation_size` |
| 생성 시간 | `CREATE INDEX` 소요 시간 |
| 삽입 처리량 | 행이 늘어나는 동안 구간별 TPS와 p99 지연 (성장 중 튀는 구간이 있나) |
| 읽은 페이지 수 | `BUFFERS`의 shared hit/read |

### 실험 2. B-tree 높이 직접 보기

- `pageinspect` 확장의 `bt_metap()`으로 행 수별 트리 레벨 확인.
- bigint 키와 긴 문자열 키에서 높이 비교 -> "3~4단계" 주장 확인.

### 실험 3. 직접 만든 자료구조로 성장 비용 보기

- Kotlin(또는 Java)으로 페이지 크기(예: 8KB) 노드를 가진 B+tree와 해시 테이블(전체 리해싱 / 점진 분할 두 가지)을 만든다.
- 키를 계속 넣으면서 삽입 한 번의 지연을 기록하고, 리해싱 순간 지연이 얼마나 튀는지, B+tree split은 어떤지 그래프로 본다.
- 조회 한 번에 닿는 노드(페이지) 수를 센다.

### 실험 4. InnoDB Adaptive Hash Index (선택)

- MySQL에서 `innodb_adaptive_hash_index` ON/OFF로 같은 동등 조회 부하를 걸어 처리량 비교.
- B-tree 위에 해시를 "캐시로" 얹는 설계가 왜 나왔는지 확인.

### 실험 5. 복합 인덱스 앞 컬럼 규칙 (선택)

- `(seller_id, created_at)` btree에서 `seller_id = ?`, `seller_id = ? AND created_at BETWEEN`, `created_at BETWEEN`만 쓰는 쿼리의 실행 계획 비교.
- 해시는 복합 키의 일부만으로 찾을 수 없다는 점 확인.

## 4. 물류 주제와 연결

`~/project/logistics-system/`과 이어지는 지점이다.
- 주문번호로 한 건 찾기(동등 조회) vs 셀러의 오늘 주문 목록(범위 + 정렬) -> 같은 테이블에 어떤 인덱스를 둘까.
- 멱등 키 확인(동등 조회만, 쓰기 많음) -> 해시나 KV(DynamoDB, Redis)가 맞는 자리인가.
- 추적 이벤트(쓰기 폭주, 주문 ID + 시각 범위) -> LSM 계열(DynamoDB 파티션 키 + 정렬 키)이 맞는 이유.
